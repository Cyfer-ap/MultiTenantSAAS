## 3. Current role model

Tenant roles:

```text
TENANT_ADMIN
TENANT_MANAGER
TENANT_USER
```

Project roles:

```text
PROJECT_LEAD
MEMBER
```

The model is stable but fixed. It cannot represent arbitrary management depth, departments, direct reports, subtree authority, or tenant-defined roles.

## 4. Authorization-v2 objective

Introduce a hybrid authorization system:

```text
Permission-based RBAC
+
Organizational hierarchy
+
Scoped role assignments
+
Relationship-based access
+
Limited contextual rules
```

The system must answer:

```text
What action may this user perform?
Within which organizational or resource scope?
Because of which role, relationship, or delegation?
```

## 5. Target organizational model

A tenant may contain arbitrary depth:

```text
Tenant
└── Division
    └── Department
        └── Team
            └── Subteam
                └── Additional nested units
```

Users may have reporting chains such as:

```text
Manager
└── Assistant manager
    └── Manager
        └── Team lead
            └── Member
```

No fixed manager-level columns may be introduced.

## 11. Phase F — Incremental module migration

Migrate one vertical slice at a time:

```text
1. Organization management
2. User read/manage operations
3. Invitations
4. Project operations
5. Project memberships
6. Tasks
7. Tenant audit-log access
8. Account/security administration
```

During migration:

```text
Legacy fixed-role rules remain available.
New permission checks use a compatibility mapping.
Each migrated module receives cross-scope tests.
```

Do not convert every endpoint in one change.


## 13. Phase H — Explain access

Add an administrative inspection capability:

```text
Why can user A perform action X on resource Y?
Why was access denied?
Which role assignment supplied the permission?
Which organizational path placed the resource in scope?
Was access delegated?
When does access expire?
```

## 14. Required invariants

```text
No organizational cycles
No unit may become its own descendant
No cross-tenant parent relation
No cross-tenant role assignment or delegation
No user may assign authority they do not possess
No delegation may exceed the delegator's scope
No lower-authority user may modify a protected higher-authority assignment
At least one tenant administrative safety path must remain
Deactivated or expired assignments cannot grant access
```

## 17. Production-aware rules during expansion

```text
Use Flyway for every schema change.
Avoid H2-only schema design.
Keep secrets externalized.
Use tenant-scoped repositories.
Centralize authorization.
Audit sensitive changes.
Paginate collection APIs.
Preserve stable error contracts.
Add tests before migrating the next module.
Never trust frontend guards as authorization.
```

## 19. Success criteria

```text
A tenant can model an arbitrary organization tree.
Managers can receive authority over direct reports or full subtrees.
Users with the same role can have different scopes.
Tenant-defined roles contain explicit permissions.
Projects can be controlled by tenant, unit, membership, or project scope.
Delegation cannot escalate authority.
Every decision is tenant isolated and auditable.
Administrators can understand why access was allowed or denied.
The original MVP behavior remains covered by regression tests.
```
